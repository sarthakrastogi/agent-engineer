# Dev lifecycle and CLI

How an Agent Script agent goes from a local file to a live version: project layout,
metadata, every relevant `sf` command, org and agent-user setup, versioning, CI/CD and
migration. Commands and flags are checked against `@salesforce/plugin-agent` 2.3.0
(Nov 2026) and `@salesforce/plugin-org`. Run `sf <cmd> --help` before using a flag this
file doesn't list.

## Two metadata domains

```text
AUTHORING (you edit this)                RUNTIME (publish creates this; never hand-edit)
aiAuthoringBundles/<Name>/               bots/<Name>/
  <Name>.agent         Agent Script        <Name>.bot-meta.xml        Bot (one per agent)
  <Name>.bundle-meta.xml                   v1.botVersion-meta.xml     BotVersion (one per publish)
                                         genAiPlannerBundles/<Name>_v1/
                                           <Name>_v1.genAiPlannerBundle   compiled agent
                                           localActions/                  subagent-scoped actions
                                         genAiPlugins/, genAiFunctions/   (legacy builder topics/actions)
```

| Type | What it is | Who writes it |
|---|---|---|
| `AiAuthoringBundle` | `.agent` source + `bundle-meta.xml` (`<bundleType>AGENT</bundleType>`) | You |
| `Bot` / `BotVersion` | Agent container and one row per published version; SOQL-queryable as `BotDefinition` / `BotVersion` | Publish |
| `GenAiPlannerBundle` | Compiled definition per version (subagents, actions, `plannerSurfaces` for channels) | Publish |
| `GenAiPlugin` / `GenAiFunction` | Topics/actions authored in the legacy builder or Asset Library | Legacy builder |
| `GenAiPromptTemplate` | Prompt Builder template, the target of `prompt://` actions | You or Prompt Builder |
| `AiEvaluationDefinition` / `AiTestingDefinition` | Agent tests (Testing Center vs Agentforce Studio runner) | `sf agent test create` |
| `BotTemplate` | Packaged agent template (legacy, non-Agent-Script agents only) | `sf agent generate template` |

- `Agent:<Name>` is a CLI pseudo-type that retrieves Bot + BotVersion + GenAiPlannerBundle +
  GenAiPlugin. It does **not** include `AiAuthoringBundle`; ask for that type explicitly.
- `GenAiPlannerBundle`, `AiAuthoringBundle` and `GenAiFunction` are Metadata API types, not
  sObjects. `SELECT … FROM GenAiPlannerBundle` fails with `INVALID_TYPE`. Query
  `BotDefinition`, `BotVersion` and `GenAiPlannerDefinition` (it has `PlannerType`) instead.

### bundle-meta.xml and the version lock

```xml
<?xml version="1.0" encoding="UTF-8"?>
<AiAuthoringBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <bundleType>AGENT</bundleType>
    <!-- <target>My_Agent.v2</target>  present = locked to published v2, read-only -->
</AiAuthoringBundle>
```

- **Naked bundle** (`My_Agent/`, no `<target>`): points at the org's highest DRAFT. It's
  the only writable copy.
- **Version-suffixed bundles** (`My_Agent_1/`, `My_Agent_2/`) are published snapshots
  retrieved from the org. Deploying them with changes fails ("content cannot be changed on
  a locked version"); deploying them unchanged is a no-op. Use them for diffs and audit.
- If you retrieve `AiAuthoringBundle:My_Agent` after a publish, the file comes back with
  `<target>` set and your next deploy fails. Fix: delete the `<target>` line and redeploy.
- Don't put extra elements in bundle-meta.xml: `Required fields missing: [BundleType]`
  means the XML isn't minimal.

## Project layout

```text
my-agent-project/
  sfdx-project.json            packageDirectories, sourceApiVersion = the org's API version (recipes use 68.0; migration API needs 67.0+)
  config/project-scratch-def.json
  specs/                        agent-spec + test-spec YAML (NOT metadata; not deployed)
  force-app/main/default/
    aiAuthoringBundles/<Agent>/ <Agent>.agent, <Agent>.bundle-meta.xml
    classes/                    @InvocableMethod Apex behind apex:// actions (+ tests)
    flows/                      autolaunched flows behind flow:// actions
    genAiPromptTemplates/       prompt:// templates
    permissionsets/             <Agent>_Access.permissionset-meta.xml
    lightningTypes/, lwc/       Custom Lightning Types and renderers
    bots/, genAiPlannerBundles/ retrieved by publish — commit them for audit, never edit
    aiEvaluationDefinitions/    generated by `sf agent test create`
```

- Find the package directory from `sfdx-project.json` (`default: true`). It isn't always
  `force-app`.
- Keep `aiEvaluationDefinitions/` out of broad `--source-dir force-app` deploys. That
  metadata type can stall a deploy for minutes. Deploy by `--metadata` instead.

## The lifecycle

```text
generate ──► edit .agent ──► validate ──► preview (simulated → live) ──► test
   │                              ▲                │
   └── backing code: deploy Apex/Flow/Prompt ──────┘
                                                   ▼
                            publish (new BotVersion, inactive) ──► activate ──► channels
```

| Step | Command | Touches org? | Notes |
|---|---|---|---|
| Spec (optional) | `sf agent generate agent-spec` | LLM in org | Generates topics from role/company. Its output feeds `--spec` |
| Scaffold | `sf agent generate authoring-bundle` | LLM in org | `--no-spec` for boilerplate |
| Edit | `.agent` in editor with the Agent Script LSP | No | See `coding-assistant-tooling.md` |
| Validate | `sf agent validate authoring-bundle` | Compile API | Syntax and compilation only |
| Deploy draft | `sf project deploy start --metadata AiAuthoringBundle:<Name>` | Yes | DRAFT visible in Builder. Creates no Bot |
| Preview | `sf agent preview start/send/end` | Yes | Simulated or live actions |
| Publish | `sf agent publish authoring-bundle` | Yes | Compiles, creates Bot/BotVersion/GenAi*, retrieves them |
| Activate | `sf agent activate` | Yes | One active version per agent |
| Test | `sf agent test create/run` | Yes | Runs against the **activated** version |

**Deploy vs publish.** Deploy only stages source into the authoring domain. Changes to
`reasoning: actions:` (invocations and transitions) only reach runtime through publish.
Publish is self-contained: a new bundle can be published with no prior deploy.

## Command reference

All commands take `-o/--target-org` and `--api-version`. Put `--json` on every command an
agent runs, read stdout as JSON, and read stderr separately. Never `2>&1`; it corrupts the
JSON.

### Generate

```bash
# Agent spec (topics drafted by the org's LLM). --type customer|internal, --max-topics 1-30 (default 5)
sf agent generate agent-spec --type customer --role "Handle order and return questions" \
  --company-name "Acme" --company-description "Online outdoor retailer" \
  --tone casual --agent-user agent.user@acme.example --output-file specs/orderAgent.yaml

# Authoring bundle — non-interactive form needs --name and (--spec | --no-spec) with --json
sf agent generate authoring-bundle --json --no-spec --name "Order Agent" --api-name Order_Agent
sf agent generate authoring-bundle --json --spec specs/orderAgent.yaml --name "Order Agent" \
  --api-name Order_Agent --output-dir force-app/main/default --force-overwrite
```

`--name` is the label (spaces allowed, becomes `agent_label`). `--api-name` is the developer
name (letters, digits and underscores, max 80, unique in the org). People swap them often.
Without `--no-spec` or `--spec` the command waits for interactive input.

### Validate, publish, activate

```bash
sf agent validate authoring-bundle --json --api-name Order_Agent
sf agent publish authoring-bundle  --json --api-name Order_Agent [--skip-retrieve] [--verbose|--concise]
sf agent publish authoring-bundle  --json --api-name Order_Agent --source-type Bot   # first publish of a converted Einstein Bot
sf agent activate   --json --api-name Order_Agent --version 3   # --json without --version activates latest
sf agent deactivate --json --api-name Order_Agent
```

- `--version` is the `N` in `bots/<Name>/vN.botVersion-meta.xml`.
- Publish creates an **inactive** version. "No valid version available" in preview means
  you forgot to activate.
- The publish response doesn't say which version it created. Read `bots/<Name>/` after the
  retrieve, or query `BotVersion`.
- The default Agentforce agent's activation status can't be changed (`agentIsDefault`).

### Preview (programmatic)

```bash
SID=$(sf agent preview start --json --authoring-bundle Order_Agent --simulate-actions | jq -r .result.sessionId)
sf agent preview send --json --authoring-bundle Order_Agent --session-id "$SID" -u "Where is order 1001?"
sf agent preview end  --json --authoring-bundle Order_Agent --session-id "$SID"   # prints traces path
sf agent preview sessions --json
sf agent preview end --json --all --authoring-bundle Order_Agent --no-prompt       # cleanup
```

| Flag | Where | Meaning |
|---|---|---|
| `--authoring-bundle <Name>` | start/send/end | Local `.agent` (compiled on the fly). Must appear on all three calls |
| `--api-name <Name>` | start/send/end | Published **and activated** agent. Always live actions |
| `--simulate-actions` / `--use-live-actions` | `start` only, required with `--authoring-bundle` | LLM-mocked vs real Apex/Flow/Prompt in the org |
| `--context-variables 'Name=v,$Context.X=v'` | start (and bare `preview`) | Seed state vars (bare name) or linked vars (`$Context.`). Text only |
| `--context-variables-json '[{"name":"gate","type":"Boolean","value":true}]'` | start | Typed: Text, Date, DateTime, Money, Ref, Boolean, Number, Object, List, Json |
| `-x/--apex-debug`, `-d/--output-dir` | bare `preview` | Apex replay debug logs; transcript dir (default `./temp/agent-preview`) |

The bare `sf agent preview` is an interactive REPL (exit with ESC). Coding agents must use
start/send/end. Context-variable flags arrived in plugin-agent 1.43 (Text) and 2.2.0
(typed). Older docs that say preview can't inject variables are out of date.

### Traces (local, from preview sessions)

```bash
sf agent trace list --json --agent Order_Agent --since 2026-11-01
sf agent trace read --json --session-id "$SID"                         # per-turn summary
sf agent trace read --session-id "$SID" --format detail --dimension actions   # actions|grounding|routing|errors
sf agent trace read --session-id "$SID" --format raw --turn 2
sf agent trace delete --agent Order_Agent --older-than 7d --no-prompt
```

Trace files live at `.sfdx/agents/<Bundle>/sessions/<sessionId>/traces/<planId>.json`.
Production traces live in Data Cloud (Session Tracing), not here.

### Retrieve, deploy, delete, open

```bash
sf project deploy start   --json --metadata ApexClass Flow GenAiPromptTemplate    # backing code only (space-separated)
sf project deploy start   --json --metadata AiAuthoringBundle:Order_Agent
sf project retrieve start --json --metadata AiAuthoringBundle:Order_Agent
sf project retrieve start --json --metadata "AiAuthoringBundle:Order_Agent_*"     # all published snapshots (quote it)
sf project retrieve start --json --metadata Agent:Order_Agent                      # runtime graph
sf project delete source  --json --metadata AiAuthoringBundle:Order_Agent          # unpublished only
sf org open authoring-bundle                     # Builder list (no --json: it only prints the URL)
sf org open agent --api-name Order_Agent [--version 2] [--url-only]
sf org open agent --authoring-bundle Order_Agent
```

- Routine backing-code deploys must not include `AiAuthoringBundle`. A stale bundle in a
  broad deploy overwrites the DRAFT someone is editing in Builder.
- A published agent can't be deleted through the Metadata API (circular dependencies).
  Delete it in Setup, or let the scratch org expire. Use unique names for throwaway agents.
- Don't rename an agent in place. Create a new one and deprecate the old one.
- Source tracking (`sf project retrieve/deploy` without `--metadata`, and VS Code
  push/pull) has returned `UnsupportedBundleTypeError: AiAuthoringBundle` on some versions.
  Use explicit `--metadata` *(verify in your org)*.

### Agent Data Library and MCP (CLI-managed resources)

- `sf agent adl create|get|list|status|update|upload|delete` and `sf agent adl file add|list|delete`
  manage Agentforce Data Libraries. `--source-type sfdrive|knowledge|retriever`,
  `--index-mode basic|enhanced`, `--wait`.
- `sf agent mcp create|get|list|update|delete|fetch` and `sf agent mcp asset list|replace`
  register external MCP servers (`--server-url`, `--auth-type OAUTH|NO_AUTH`). These
  commands are **preview** state.

Grounding and MCP design are covered in the RAG/integration references.

## Org and agent-user setup

### Scratch org

```json
{
  "edition": "Developer",
  "features": ["Einstein1AIPlatform", "ServiceCloud", "LiveAgent", "LiveMessage",
               "Communities", "Sites", "EnableSetPasswordInApi"],
  "settings": {
    "EinsteinGptSettings": { "enableEinsteinGptPlatform": true },
    "agentPlatformSettings": { "enableAgentPlatform": true },
    "omniChannelSettings": { "enableOmniChannel": true }
  }
}
```

Taken from `trailheadapps/agent-script-recipes`. The Service/Messaging/Communities
features are only needed for service agents and channels. Their CI waits about 120 s after
`sf org create scratch` before deploying, because AI features provision asynchronously.
Assign `EinsteinGPTPromptTemplateManager` to the dev user before deploying prompt
templates.

### Service agent vs employee agent

| | `AgentforceServiceAgent` (default) | `AgentforceEmployeeAgent` |
|---|---|---|
| Runs as | A dedicated agent user (Einstein Agent User profile/licence) | The logged-in employee |
| `access.default_agent_user` | **Required** | Omit, or `None` |
| Sharing | The agent user's access, the same for every conversation | The employee's own sharing |
| Permission sets on | The agent user | Each employee |

`default_agent_user` belongs in the top-level `access:` block. `config.default_agent_user`
still works but is deprecated: if both are set, `access` wins and the linter warns.
`access` is only valid at the top level.

### Create the agent user

```bash
# Preferred (plugin-org): Einstein Agent User profile + AgentforceServiceAgentBase,
# AgentforceServiceAgentUser, EinsteinGPTPromptTemplateUser; checks licences; no password
sf org create agent-user --json --base-username service-agent@acme.example --first-name Order --last-name Agent

# Then grant what the actions need
sf org assign permset --json --name Order_Agent_Access --on-behalf-of <agent-username>
```

`<Agent>_Access` must grant `classAccesses` for **every** Apex class behind an `apex://`
target in every subagent, plus object and field access for whatever the flows and Apex
touch. Rules:

- **Don't rely on the auto-generated `NextGen_<Agent>_Permissions`.** It has been observed
  missing classes, which gives "invocable action … does not exist" at runtime.
- **The planner checks permissions for all actions at startup.** One missing class fails
  the whole agent, not just one subagent.
- **Apex with `WITH USER_MODE` fails silently without object access.** It returns 0 rows
  and no error: works in simulated preview, empty in live preview.
- **Knowledge/Data Library agents also need Data Cloud access.** One of the
  `GenieDataPlatformStarterPsl` PSL, `GenieUserEnhancedSecurity` or `DataCloudUser`,
  depending on org shape, plus Data Space scope on that permset (UI only today).
- **"Internal Error, try again later" on first publish is often a missing
  `AgentforceServiceAgentUser`,** or a `default_agent_user` that isn't an active
  Einstein Agent user.

**Portable username.** Usernames are globally unique, so a hard-coded `default_agent_user`
breaks in the next org. Do what the recipes repo does: commit a placeholder and substitute
it per org in CI.

```bash
AGENT_USER=$(sf org create agent-user --json -o ci | jq -r .result.username)
grep -rl '__AGENT_USER_PLACEHOLDER__' force-app --include=*.agent \
  | xargs sed -i "s/__AGENT_USER_PLACEHOLDER__/${AGENT_USER}/"
```

## Versioning and activation

- Every publish adds a `BotVersion` and a `<Name>_vN` planner bundle, whether or not the
  content changed. Publish deliberately, not on every edit.
- Pro-code has one DRAFT per agent. Publish locks it and the next deploy opens a new DRAFT.
  Only Builder can create extra parallel DRAFTs.
- Only one version is active at a time. Activating vN deactivates the previous one.
- Changing `default_agent_user` needs no version active. Deactivate first, then republish
  and reactivate.

**Rollback.** Reactivate the previous version. It's instant and needs no redeploy.

```bash
sf data query --json -q "SELECT VersionNumber, Status FROM BotVersion WHERE BotDefinition.DeveloperName='Order_Agent' ORDER BY VersionNumber DESC LIMIT 3"
sf agent activate --json --api-name Order_Agent --version 4
```

Keep the last-known-good version number in the release notes.

## CI/CD

Rules:

- Validate and test in a **sandbox or scratch org**.
- Promote the **same source** to prod.
- Publish and activate in prod only from a protected branch, behind a human approval.

```yaml
# .github/workflows/agent.yml (sketch — adapt auth, org aliases, names)
on: { pull_request: { paths: ['force-app/**', 'specs/**'] }, push: { branches: [main] } }
jobs:
  verify:                      # every PR, against a scratch org or CI sandbox
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm i -g @salesforce/cli && sf --version
      - run: echo "${{ secrets.CI_SFDX_AUTH_URL }}" > a.txt && sf org login sfdx-url -f a.txt -a ci -s
      - run: sf project deploy start --json --metadata ApexClass Flow GenAiPromptTemplate PermissionSet -o ci
      - run: sf apex test run --json -l RunLocalTests -w 20 -o ci
      - run: sf agent validate authoring-bundle --json --api-name Order_Agent -o ci
      - run: sf agent publish authoring-bundle --json --api-name Order_Agent -o ci
      - run: sf agent activate --json --api-name Order_Agent -o ci
      - run: sf agent test create --json --spec specs/Order_Agent-testSpec.yaml --api-name Order_Agent_Regression --force-overwrite -o ci
      - run: sf agent test run --json --api-name Order_Agent_Regression --wait 20 --result-format json -o ci > results.json
      - run: python3 scripts/gate_agent_tests.py results.json --min-pass 0.9   # exit code alone is NOT a gate
  release:                     # main only, environment with required reviewers
    needs: verify
    if: github.ref == 'refs/heads/main'
    environment: production
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm i -g @salesforce/cli
      - run: echo "${{ secrets.PROD_SFDX_AUTH_URL }}" > a.txt && sf org login sfdx-url -f a.txt -a prod
      - run: sf project deploy start --json --metadata ApexClass Flow GenAiPromptTemplate PermissionSet -o prod --test-level RunLocalTests
      - run: sf agent publish authoring-bundle --json --api-name Order_Agent -o prod
      - run: sf agent activate --json --api-name Order_Agent -o prod     # record previous version first
```

`sf agent test run` exits 0 when assertions fail. It only exits 1 when a test case
*errors*. Parse the results and gate on pass rate (`testing-and-evals.md` → CI gate).

**Packaging.** `sf agent generate template` builds a `BotTemplate` for 2GP managed packages
from legacy agents only. It refuses Agent Script agents. For Agent Script, ship source, or
use unlocked packages *(verify subscriber editability in your org)*.

## Migration

| From | Path |
|---|---|
| Legacy Agentforce agent (topics in Agent Builder, `GenAiPlannerBundle` with `PlannerType` `AiCopilot__ReAct` / `SentOS__SearchAgent`) | Builder's upgrade, or `POST /services/data/v67.0+/connect/migrateAgentToNga` with `{"botVersionId":"0X9…"}` via `sf api request rest` |
| Einstein Bot (`BotDefinition.Type = 'Bot'`) | Convert to an Agent Spec, then author `.agent`. Publish the first time with `--source-type Bot` |
| Agents created with `sf agent create` (spec → topics, no Agent Script) | Treat as legacy. Salesforce no longer recommends `agent create` |

**Legacy → Agent Script with `migrateAgentToNga`**

1. Pick a non-NGA `BotVersion`: join `botVersion-meta.xml` → `genAiPlannerName` →
   `GenAiPlannerDefinition.PlannerType`. `Atlas__ConcurrentMultiAgentOrchestration` means
   it's already NGA.
2. The call is **mutating**. It creates a new bundle and bundle version, and the legacy
   versions stay untouched.
3. The response is large (inline `agentScript`). Keep `bundleId`, `bundleVersionId`,
   `bundleVersionApiName` and `conversionWarnings`.
4. Retrieve with `AiAuthoringBundle:<bundleVersionApiName>`, review the warnings (subagents
   that resolved to no actions are common), and fix the script.
5. Regression-test the draft (`--authoring-bundle`) against the still-active legacy agent
   (`--api-name`) on the same utterances. Classify each case against the *intended*
   route/actions, not against legacy behaviour, which may itself be wrong.
6. **Blocker:** developer names ending in `_<digits>` (`Agent_01`) get confused with
   version suffixes and can't be round-tripped from the CLI. Rename first (`Agent_v01`),
   and update email configs, `package.xml` and Agent API callers too.

**Einstein Bot → agent.**

- **Menus become intent-based subagent routing.**
- **Not converted:** bot goals, rich messaging components, file attachments, mid-chat
  language switches, and non-Apex/Flow actions such as object search.
- **Reconfigure after conversion:** the agent user, the channels and Omni-Channel flows.
- **Review before activating:** the output is a committed, unactivated version.

The removed `sf bot …` commands don't exist in sf v2. Use `sf agent` and `sf project`.

## Anti-patterns

- Publishing on every edit. You get version inflation, and DRAFT state gets lost. Iterate
  with validate and preview, and publish when you're ready to release.
- Editing anything under `bots/`, `genAiPlannerBundles/` or version-suffixed bundles.
- `sf project deploy start --source-dir force-app` as a habit. It ships stale bundles and
  stalls on test metadata.
- Assuming publish activated the agent, or that a green `validate` means publish will
  pass. Validate doesn't check `default_agent_user`, licences or target existence.
- Stub `@InvocableMethod` classes with the wrong I/O. Deploy only checks that the target
  exists, so parameter mismatches surface at runtime.
- Treating `sf agent test run` exit 0 as "tests passed".
